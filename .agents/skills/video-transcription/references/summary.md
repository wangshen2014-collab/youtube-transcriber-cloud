# 视频总结与按需分析

## 获取足够的原始内容

1. 优先复用本次提供的转录稿、字幕或已保存的同视频结果，核对视频身份、范围、日期与来源；已有可用文字时不为总结重新跑 Whisper。
2. 可读取同视频可访问字幕，包括自动字幕，并注明其来源及可能的识别错误；这是总结的内容来源，不宣称进行了全新高精度转录。只有标题、简介或搜索片段不足以总结全片。
3. 长文按顺序完整阅读或分块处理，保留每块的观点、论据、转折与定位，最后合并主题；不能只读开头、只抽样或只搜索熟悉关键词就称为完整总结。工具截断时继续读取未覆盖部分。
4. 只有音视频且无可用文字时，可使用当前真实可用的直接理解能力；否则在用户未禁止语音识别时用云端 medium/beam3 生成内部工作稿。需要识别时读取 [transcription.md](transcription.md) 中的环境、输入、配置、预算和运行纪律。无需为了内部工作稿先取得 GitHub 写权限。
5. 内部工作稿不是用户要求的交付物，不默认发布 TXT/SRT/JSON 或远程检查点；避免使用会自动上传的批处理入口，可用现有单项 CLI，仅写当前任务目录。明确禁止识别时不得执行此回退。
6. 缺少输入、无法访问或内容不全时，说明具体缺项及覆盖范围；已有材料支持局部总结就标明“基于所提供片段”。不要根据题材常识补齐观点。
7. 只读了音轨/字幕就说明基于口述或字幕；不能声称看过图表、PPT、动作或画面。画面对解释重要且可用工具支持时检查相关画面，缺失时指出影响。不要凭口述猜图中的数值。

## 如何总结

- 默认使用中文，用户指定其他语言时遵循；术语保留必要原文。
- 开头用一两句话交代视频讨论的问题与核心主张；随后按实际主要观点组织，每条配对应的理由、数据、案例、推理或反例。不强制固定条数，避免逐段复述。
- 区分“讲者声称的数据/事实”“讲者观点/预测”和“举例或类比”。没有进行外部核实就不把讲者说法改写成已经证实的事实。
- 保留影响结论的前提、适用范围、时间、条件、例外与不确定性。不能把“如果……可能”压缩成确定结论。
- 观点与论据逐一对应。未提供支撑时写“视频未给出具体依据”；不从外部知识替讲者补证据，不替不同受访者合成一致立场。
- 数字或术语存疑且影响主旨时，回查上下文或关键音频；无需为口头禅、推广段或每个措辞进行高精度复核。默认关键音频复核预算约源时长5%，单一疑点最多两次机器复核，无法确认就省略非必要精确数字或明确标注待核。
- 有可靠时间戳时可附关键定位，无时间依据不编造。默认少量必要引用，优先用自己的话归纳，不交付整片逐字稿。
- 仅总结时不附加自己的评价、投资建议、外部行情或事实核查。只为取得视频或字幕的检索不等于获得了事实核查授权。

## 用户要求分析时

- 将“视频总结”和“分析”清楚区分。按实际请求评价论证强弱、证据相关性、隐含假设、因果与相关、替代解释、内部矛盾或关键缺口；避免套空泛清单。
- 标明哪些是基于视频内部的判断，哪些是外部证据或自己的推断。没有外部核实不能声称事实已被证伪。
- 用户要求核查、最新情况，或分析确需当前/专业事实时，用可用工具查权威一手来源并给出链接；未能核实则保留不确定性。对可能变化的事实不要靠旧记忆下结论。
- 请求“分析”不自动等于要求个性化投资、医疗或法律建议。聚焦内容、证据与推理，按用户实际范围回答。

## 交付与保存

默认在当前聊天直接交付总结；用户要求文件时生成 TXT，要求分析则文件也区分总结与分析。
用户明确授权保存到原仓库时，只保存本次总结/所要求的分析，标记为总结，不伪装为逐字转录或覆盖已有转录。
发布沿用转录参考的保留旧文件、预期分支头校验及下载读回验证规则，但不要求总结文本与 SRT 一致，也不为总结补造 SRT。
发布工具若仅支持逐字稿，改用可用的通用 GitHub 文件工具，不改产品代码或顺带上传工作稿。
